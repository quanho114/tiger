# V01 Contract Decisions

updated 2026-09-22 v1.0

## Scope

This record freezes Concierge V2 contracts and integration defaults for V02, V05 and V08. It does not activate V2, migrate runtime state, alter legacy Concierge behavior, create a database migration, or delete data.

| Client state | `src/features/concierge/useConcierge.ts` keeps current chat state in React memory, but applies `cart_addition` directly to the real cart. | V04 / V13 |

The legacy frontend and server Concierge DTOs are separately defined and already differ in supported intents, actions, cards, and status fields. V2 owns the canonical definitions in `supabase/functions/_shared/contracts/concierge-v2.ts`; later consumers must derive from that module instead of extending both legacy type files.

## Frozen protocol

- Protocol literal: `concierge-v2`.
- JSON completion and SSE `complete` events carry the same validated completion payload. Legacy progress/card/message events remain a V03 compatibility concern.
- Existing-session turns contain a server-issued opaque capability, session ID, request ID, and expected state version. The capability never enters model context, errors, traces, URLs, or browser persistence.
- V2 errors are closed to `UNSUPPORTED_VERSION`, `REFRESH_REQUIRED`, `UNAUTHORIZED`, `OWNERSHIP_MISMATCH`, `SESSION_EXPIRED`, `STATE_CONFLICT`, `IDEMPOTENCY_MISMATCH`, `DEPENDENCY_UNAVAILABLE`, `AMBIGUOUS_ACCEPTANCE`, `ALLERGY_UNVERIFIED`, `PRICE_CHANGED`, `ITEM_UNAVAILABLE`, `INVALID_HANDOFF`, and `INTERNAL_SAFE_FAILURE`.
- A capability may only be generated by the server. Guest ownership is capability-based; authenticated sessions additionally bind the verified server-side user identity. Login, logout, account switch, reload, and explicit reset begin a fresh V2 session. Guest state is never promoted to durable memory.
- Every session mutation applies a compare-and-swap against `expected_state_version`. The bounded idempotency record binds request ID to an operation hash: a matching retry replays its stored result; a mismatched reuse returns `IDEMPOTENCY_MISMATCH`.

## V02 session-store decision

- Current production adapter: the existing Supabase PostgreSQL pool and private
  `public.concierge_v2_sessions` table. The original Redis adapter was removed
  on 2026-09-23; historical V02 reports retain the earlier design evidence.
- Missing table or unavailable database returns `DEPENDENCY_UNAVAILABLE`;
  production never falls back to Edge-isolate RAM or a success-looking stub.
- Tests may inject an in-memory backend and deterministic clock. Real session
  integration tests use an isolated, marked PostgreSQL database.
- One atomic session record contains messages, summary, constraints, pending suggestion identities, draft, version, expiries, actor binding, and bounded idempotency records. It expires after 45 minutes of idle time or four hours absolute lifetime, checked on read and mutation.
- The existing retention endpoint physically deletes expired rows. PostgreSQL
  backup retention must account for session text after row deletion.

## V05 memory and extraction decisions

- Memory is disabled until an authenticated customer explicitly enables it. Durable values are compact, allowlisted food preferences and constraints only; no transcript, raw utterance, model reasoning, address, diagnosis, capability, or provider response is durable memory.
- Current-turn constraints override remembered values. Session allergy constraints still apply when memory is disabled.
- V06 schedules extraction through a durable bounded worker queue. A queue job stores an opaque V2 session reference, deadline, user ID, and expected `memory_epoch`; it does not store raw messages or a transcript. The worker reads the still-live TTL session only when eligible, then drops work that is expired, disabled, deleted, or epoch-mismatched. Queue failure does not fail chat and yields only a content-free metric.
- Disable, forget-all, and account deletion each increment `memory_epoch`. Individual deleted behavioral facts create a value-free suppression key. Forget-all pauses regeneration until a future explicit enablement.
- Behavioral aggregation uses only completed, non-cancelled eligible orders in the prior 90 days. The current status model has only `refunded` payment status and lacks reliable non-refunded line-level semantics, so refunded and partially refunded orders are excluded until V07 can prove an authoritative schema path. Party size is not inferred from items, total, or weak signals; it requires a verified stored visit/reservation field.

## V08 catalog and food-safety decisions

- Menu IDs, prices, availability, ingredient and allergen/cross-contact assertions come only from authoritative catalog output.
- Missing or unverified ingredient, allergen, or cross-contact information maps to `ALLERGY_UNVERIFIED`; no handoff line may be marked safe in that state.
- Catalog search returns 5–8 candidates after filtering hard constraints, availability, price, and ordering mode. Draft and handoff revalidate authoritative price, availability, mode, and allergy status.

## Draft and handoff decisions

- Candidate recommendations and accepted draft lines are distinct. An ambiguous acceptance returns `AMBIGUOUS_ACCEPTANCE` and clarification; it never mutates the draft.
- “Chốt” enters review only. It cannot mutate the real cart, create an order, start checkout, charge payment, or confirm a reservation.
- One reviewed draft version exports one named set. After a successful handoff, edits create a new set/version that needs new review and handoff; the prior exported quantities are not silently re-exported.
- V13 returns a short-lived, actor/session/version-bound authoritative handoff snapshot with an opaque stable handoff ID. A retry returns the same ID and lines while valid. The existing cart atomically persists normal cart lines and the applied opaque handoff marker for its normal lifetime, preserving existing lines and notes. This is an idempotent client application protocol, not a distributed transaction.

## Orchestration, observability, and rollout

- V2 permits at most three model calls and six tool executions per turn. Dependent calls and all mutations serialize. Initial context limits remain 6,000 input tokens per model call, 12,000 per turn, 2,000–4,000 typical input, 200–400 token summary/fact budgets, and 5–8 menu candidates.
- V2 tools exclude checkout, payment, order submission, and reservation confirmation. Provider failure must return a safe failure rather than a deterministic success-looking reply.
- Content-free traces retain aggregate outcome, provider/model identifier, token counts, latency, and coarse cost bucket for 14 days by default. They exclude messages, prompts, facts, addresses, capabilities, bearer tokens, keys, provider failure bodies, and tool argument dumps.
- V2 is server-controlled and default-off. V03 owns feature-flag registration and JSON/SSE version negotiation. Once enabled, legacy guest chat/action/feedback writers must receive `REFRESH_REQUIRED` or use a privacy-safe adapter; they must not keep writing legacy guest transcripts.

## Contract examples

| Scenario | Required result |
| --- | --- |
| Success | V2 completion payload contains request/response IDs, session metadata, phase, and optional draft. JSON and SSE `complete` validate identically. |
| Expiry | `SESSION_EXPIRED`; UI starts a new page-lifecycle session. |
| Concurrent mutation | `STATE_CONFLICT` with no capability disclosure. |
| Reused request ID, different operation | `IDEMPOTENCY_MISMATCH`. |
| Ambiguous “OK” | `AMBIGUOUS_ACCEPTANCE` clarification; draft stays unchanged. |
| Unknown allergy | `ALLERGY_UNVERIFIED`; no accepted handoff line. |
| Price change or unavailable item | `PRICE_CHANGED` or `ITEM_UNAVAILABLE`; refreshed acceptance is required and blocked lines remain visible. |
| Repeated handoff | Same opaque handoff ID and authoritative snapshot; response does not claim a browser cart mutation. |

- V02 implements `ConciergeV2SessionStore` against the selected adapter.
- V05 implements `ConciergeV2MemoryRepository` plus additive schema/RLS.
- V08 supplies authoritative tool/catalog outputs that satisfy the food-safety boundary.

- V16 implements flags, content-free trace retention, and provider accounting.

## V03 integration additions (2026-09-22)

The shared turn schema adds only reset_conversation and feedback_proposal actions;
legacy checkout/order/reservation-confirmation actions remain invalid in V2. Existing
session/version are mandatory for actions. The ephemeral record adds bounded runtime
phase/proposal/pending-action metadata so the existing runtime can round-trip without
SQL. Serialized sessions including replay results are capped at 256 KiB. Oversize
writes fail safely; V09 owns trimming/summary behavior. V04 consumes the raw JSON V2
envelope and matching SSE complete payload.

V08 adds explicit absent allergen evidence; missing entries are unknown, never an
implicit negative. V03 adds server-only feature flags and anonymous daily feedback
counters through two additive migrations. These additions affect V04/V09/V10/V15/V16
and acceptance A01/A04/A16/A18/A19/A20/A21. They do not activate the feature.

## Full-plan integration decisions (2026-09-22)

- V10 replaces the temporary V03 legacy runtime bridge with the grounded V2
  orchestrator. Protocol dispatch lives in `public-api/concierge-protocol-handlers.ts`
  under the current gateway/handler architecture. App-shell provider paths follow
  `src/app`, `src/features` and `src/shared`; older task paths are historical.
- Shared actions now include refresh_session, review_draft, accept_prices and
  handoff_draft. Exactly one message/action/draft operation is accepted per turn.
  V2 still rejects confirm_quote and reservation confirmation.
- Ephemeral pending_items tie suggestions to item IDs/version. Handoff is stored
  with the exported draft and idempotency result. Blocks preserve line IDs, notes,
  quantities and old prices; current_unit_price_vnd is the exact displayed offer
  the user accepts. A second price change asks again. A blocked handoff returns
  committed review state with warnings and no handoff, not a misleading export.
- Handoff allergy_status is verified_safe only when declared allergies have been
  verified; not_requested means no declared allergy check. It is not an allergy
  safety guarantee. No arbitrary unknown/conflict handoff status is accepted.
- Model-facing tools are a deliberately small read-only routing surface. Search
  and recommendation cover item/availability retrieval; direct draft operations
  use server-validated customer intent. V2 booking queries open the existing
  explicit reservation UI. Numeric and safety claims use deterministic server
  templates; optional model prose is currently entirely discarded.
- The default adults=2 is not a confirmed party size. party_size_confirmed records
  explicit input; a food recommendation asks party size while unset. Explicit
  max_spice_level survives later turns. Oversized allergy sets retain an unknown
  sentinel, blocking unchecked safety rather than dropping hard constraints.
- Input budgeting uses UTF-8 bytes plus provider framing as a conservative upper
  bound. This may trim earlier than a provider tokenizer. Actual provider usage is
  recorded separately. No measured production cost/latency target is claimed.
- V15 adds migration 00004 for epoch-fenced fact correction/deletion and immediate
  purge on account-deleting transition. Extraction captures the original consent
  epoch before the turn. Suppressions survive epoch changes until explicit restore.
- V16 adds migration 00005 for shared content-free circuit state. Turn concurrency
  is guarded by a PostgreSQL transaction advisory lock plus Redis CAS. Metric
  fields intentionally omit arbitrary model names/values to avoid accidental
  content capture; provider version is tracked in release configuration evidence.
- Staged rollout uses CONCIERGE_V2_ROLLOUT_PERCENT after protocol negotiation.
  Nonselected cohorts cannot fall back to legacy writes. Emergency stop keeps V2
  protocol enabled and sets CONCIERGE_V2_DISABLED=true. See release-runbook.md.
- Normal cart lines and opaque dedup IDs persist in one storage write. If that
  required write fails, handoff application fails visibly and can retry the same
  request. Manual additions batched with handoff are included in the merge.
- Local offline readiness, independent review, human assistive-technology checks,
  live-provider quality and production operations are separate evidence gates.
